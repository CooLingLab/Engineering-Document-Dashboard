# 开发路线与文档可视化工具：首版设计

- 日期：2026-10-30
- 状态：用户已于 2026-10-30 确认，进入实施计划；尚未进入实现
- 工作名称：Development dashboard，正式名称待定
- 适用范围：首版产品设计、技术约束与验收依据

## 1. 意图与定位

这是一个帮助开发新手了解软件开发全貌的网页工具。用户打开网页、填入 GitHub 仓库，工具按开发范式展示基本路线、关联 Markdown 文档、显示环节状态，并提示建议的下一步。

用户期待的是“不再盲人摸象”：知道有哪些开发环节、每个环节为什么存在、目前文档反映什么情况，以及接下来可以做什么。它不以用户最终完成某个项目为承诺，也不要求用户严格照流程行动。

服务对象首先是个人开发者，考虑开源后其他个人使用者的体验。每次工作界面聚焦一个项目，首版不提供多项目进度总览。

## 2. 已确认的产品决定

| 方面 | 已确认决定 |
| --- | --- |
| 产品形态 | 工具自己是一个独立 GitHub 项目，部署为网页 |
| 数据入口 | 填入其他 GitHub 项目地址；首版只支持 GitHub.com，不读取本地文件夹 |
| 项目文档 | 从目标仓库的指定目录读取 Markdown，不要求复制文档到工具仓库 |
| 仓库权限 | 支持公开和用户有权访问的私有仓库 |
| 部署与授权 | 选择纯网页方案，用户自行提供 GitHub 访问令牌；首版不建设登录后端 |
| 界面逻辑 | 采用讨论草图 A：完整路线为主，选中环节后在下方显示详情 |
| 画布能力 | 拖拽、增减节点、连接环节；支持分支、并行和汇合，不自动执行开发任务 |
| 起点 | 可选常用开发范式，也可从空白画布开始 |
| 默认推荐 | 首次使用推荐一条通用开发路线 |
| 文档规范 | 工具统一提供文件夹和文件命名规范，允许用户调整 |
| 识别失败 | 仍显示指定目录中的文档，允许手动关联，不自动重命名 |
| 缺少文档 | 提示缺失，提供通用 prompt；用户可以标记“不需要”或“稍后再说” |
| 文档生成 | 工具不生成或修改项目文档；prompt 仅供复制，不自动附带项目内容 |
| 新手模式 | 首次使用默认开启，可随时关闭；增加解释，不改变流程或状态规则 |
| 状态 | 支持手动标记和 AI 内容判断；手动标记始终优先 |
| AI | 可选择在线模型、本地模型或关闭；用户主动触发分析 |
| 无 AI 使用 | 核心浏览、流程编辑、手动标记、范式提示和 prompt 复制仍可用 |
| 配置同步 | 用户自己的独立 GitHub 配置仓库，保存流程、关联和状态 |
| 分支 | 默认读取默认分支，支持切换；流程结构按项目共享，手动状态和 AI 判断按分支保存 |
| 移动文件 | 保留原关联并提示文件不可用，允许重新关联，原路径恢复后重新读取 |
| 切换范式 | 先预览，保留原流程作为可恢复的备用版本 |

下文没有直接来自用户决定的具体规则，统一视为设计者提出的首版默认方案，供本次设计审阅，不应标成用户已经逐项同意的需求。

## 3. 目标、非目标和失败情形

### 3.1 首版目标

1. 新手能从完整路线理解基本开发过程，而不必先学会任务管理工具。
2. 节点能直观看到状态和文档缺失提示，点开后能阅读原文及环节指导。
3. GitHub 上的文档更新后，网页可以重新读取；文档变化不会自动产生模型调用。
4. 熟悉开发的用户可以关闭详细解释，并按自己的习惯调整流程。
5. 用户在另一台设备重新授权并连接同一个配置仓库后，可以读取已同步的个人配置。

### 3.2 非目标

- 多项目仪表盘、团队协作、任务指派、排期、工时和功能级任务拆解。
- 代码扫描、构建、测试执行、agent 编排、自动推进开发或自动写文档。
- 从一份文档中拆出所有产品功能并分别管理开发流程。
- 本地项目目录接入、GitHub Enterprise、自建 Git 服务和其他代码托管平台。
- 自建账号系统、OAuth 登录后端、产品运营数据库、内置付费模型额度。
- 强制用户补齐全部文档、强制串行推进，或把文档数量换算为开发完成百分比。

### 3.3 应避免的失败情形

- 界面退化为任务看板，新手仍不知道路线及每个环节的意义。
- 用“找到文件”冒充“这个环节已完成”，或把文档描述当成已经验证的代码事实。
- 自动覆盖用户标记，或未经用户操作自动调用模型。
- 将私有文档、令牌或模型密钥打包进公开站点或提交到配置仓库。
- 用户换设备后误以为已经同步，实际上配置仍只是未保存草稿。

## 4. 考虑过的实现方式

| 方式 | 优点 | 代价与适用性 | 结论 |
| --- | --- | --- | --- |
| 纯网页 + GitHub API + 用户令牌 | 可以独立部署到 GitHub Pages；不需要维护服务端；项目文档留在原仓库 | 私有仓库和配置写入需要用户配置令牌；模型连接受浏览器限制 | 用户选择此方式作为首版 |
| 网页 + GitHub 登录授权服务 | 用户连接 GitHub 的体验更连贯，适合统一运营的服务 | 需要额外部署、维护授权服务和凭据处理 | 首版不采用 |

选择前者的原因是个人先用、方便开源部署、尽量不改变目标项目。目标仓库只负责提供文档，独立配置仓库负责保存本工具产生的个人配置。

GitHub Pages 承载静态网页；仓库访问和模型分析发生在访问者浏览器中。GitHub Pages 不承担后端代理、常驻同步任务或模型运行。([GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages))

## 5. 使用流程与界面

### 5.1 首次打开

1. 显示仓库地址输入框和简短产品说明。默认开启新手模式。
2. 用户连接公开仓库时可先不配置令牌；私有仓库需要提供读取令牌。
3. 默认选择仓库默认分支，明确展示当前仓库、分支和文档目录。
4. 有已同步配置时加载；没有配置时推荐通用路线，也允许选择其他范式或空白画布。
5. 使用范式的目录和命名规则读取文档，生成关联结果和缺失提示。
6. 用户需要保存配置时，连接自己创建的独立配置仓库，并提供配置写入令牌。

只读浏览不以完成配置同步或设置 AI 为前提。私有仓库的组织策略、资源所有者或令牌审批可能限制访问，应展示具体失败原因，不自动申请更宽权限。

### 5.2 主页面：路线为主

```text
项目 / 仓库          分支选择        文档目录       刷新 / 同步 / 设置

建议下一步：……                         新手模式：开启 / 关闭

                 可缩放、可拖拽的流程画布
   想法与目标 → 需求 → 设计 → 开发 → 测试 → 交付
   每个节点显示状态，以及简短的文档缺失提示

所选环节详情
   状态与来源 ｜ 相关文档列表 ｜ Markdown 阅读区
   环节说明与检查要点 ｜ 通用 prompt 的复制入口
```

画布始终是主视图，文档和解释服务于理解路线。首版优先桌面浏览器上的使用体验；窄屏允许画布平移、详情纵向阅读，不引入另一套产品逻辑。

新手模式开启时增加“为什么做、要做什么、如何检查”的简短说明；关闭时收起这些解释，保留节点、文档、状态和建议。

### 5.3 画布操作

- 添加、重命名、移动或删除环节；新增或删除连线。
- 从范式开始或空白开始；自定义环节可写名称、简短说明并手动关联文档。
- 分支和并行表示路线关系，不触发执行，也不阻止用户跳到其他环节。
- 允许画出迭代回路。推荐规则需防止循环查找；无法排出唯一下一步时，给出已有环节的有限候选并允许用户选择，不杜撰依赖。
- 删除已有环节前说明对关联和状态的影响，提供可恢复操作；移动节点不改变阶段完成度。
- 首版不自动生成自定义环节的教学材料或 prompt；可显示范式中已有的通用 prompt。

### 5.4 文档阅读与关联

只索引选定文档目录及其子目录中的 `.md` 文件。不扩展为整个代码仓库扫描。目录未找到时允许用户修改目录、查看推荐规范，继续显示路线与缺失文档建议。

匹配顺序：用户手动指定路径 > 当前项目的命名规则 > 显示为“未关联”。多个候选文件不应随意挑选，展示候选供用户选择。指定目录中的其他文档保留在“其他文档”列表中。

详情中展示只读 Markdown，支持标题、列表、表格、任务复选框的阅读和代码块。复选框不写回源文档。提供“在 GitHub 查看原文件”入口。

相对文档链接按当前分支和目录解析；超出允许读取范围的链接交给用户在 GitHub 打开，不自动读取额外文件。文档图片若支持加载，也应限制为用户明确选择的资源范围；私有文档及图片不走公开第三方代理。

关联路径失效时保留配置并提示，不删除手动状态；自动刷新发现原路径恢复后重新读取。更换关联只改变配置仓库中的路径，不修改原文件。

## 6. 范式、规范与 prompt

### 6.1 首版内容的设计者建议

首版保持少量、通俗的常用范式，具体内容在实现前可按同一结构校对：

1. **通用应用开发**：默认推荐；想法与目标 → 需求 → 设计 → 开发 → 测试 → 交付。
2. **原型 / MVP 验证**：目标 → 最小范围 → 原型 → 验证与调整。
3. **迭代开发**：本轮目标 → 需求与设计 → 开发与测试 → 回顾及下一轮；仍是基本路线，不管理功能级任务。

每个范式说明适用情况，并包含节点、默认连线、建议文档及路径、环节解释、检查要点和通用 prompt。它们是建议，用户可删减，不要求所有文档都存在。

范式按稳定 ID 和版本发布。用户采用范式后保存副本；工具升级不会直接覆盖用户调整。切换范式先预览，新方案确认应用时保留旧图、关联和当时的分支状态快照，支持恢复。恢复前说明替换范围，避免把旧状态和新节点混在一起。

### 6.2 推荐的初始命名规范

这是本设计提出的默认值，用户可以修改目录、文件名和关联：

```text
docs/development/
  01-vision.md
  02-requirements.md
  03-design.md
  04-implementation.md
  05-testing.md
  06-delivery.md
```

范式不在目标仓库自动创建目录或文件。推荐路径同时展示在缺失提示和通用 prompt 附近，供用户在外部开发工具中自行使用。

### 6.3 通用 prompt

- prompt 是随范式发布的静态内容，描述该环节要讨论的问题和建议输出。
- 只提供复制，不在工具内调用模型来生成项目文档。
- 不自动拼入仓库地址、文档正文、状态、用户身份或密钥。
- 用户可在外部 AI 工具里自行补充背景，并将产出保存到原项目。
- 自定义环节没有对应 prompt 时如实显示，不自动生成。

## 7. 状态、文档检查与下一步

### 7.1 三类信息独立显示

| 信息 | 意义 | 不能推出什么 |
| --- | --- | --- |
| 文件检查 | 已找到、缺失、路径不可用、未关联 | 找到文档不等于环节完成 |
| 内容判断 | 尚未分析、信息不足、AI 建议状态及依据 | 文档声称完成不等于代码经过验证 |
| 环节状态 | 用户手动标记，或当前有效的 AI 建议 | 缺失文档不自动等于整个项目尚未开始 |

设计者建议手动状态使用“未开始、进行中、已完成、暂缓”。没有手动值或有效 AI 判断时显示“未判断”。用户可以清除手动值，恢复使用有效 AI 建议。空文件、只有标题等可以由基础检查指出，但不冒充语义分析。

每份建议文档可以标记“需要”（默认）、“不需要”或“稍后再说”。“不需要”不再催促；“稍后再说”保持可见但暂不作为首要补充建议，用户可以恢复。文档取舍记录随对应分支保存，避免不同分支相互影响。

### 7.2 手动优先和过期判断

- 有手动状态时，主状态始终取手动值；AI 结果作为可展开参考。
- 文档变化后保留手动状态，提示依据可能变化，不自动撤销用户决定。
- AI 结果记录所用文档路径和 blob SHA、范式 / 图结构版本、分析时间、端点与模型名称。
- 相关文档、文档关联、环节说明或指导规则变化后，AI 结果标为过期，不再参与当前状态和下一步排序；手动状态变化后也不能沿用之前的 AI 下一步排序。
- 不相关的代码提交不必让所有判断失效；比较分析输入，而非仅比较整个仓库 HEAD。

### 7.3 未配置 AI 时的下一步

按范式和用户标记提供有明确来源的建议：

1. 优先关注手动“进行中”的环节。
2. 否则沿流程选择前置环节没有明确未完成项的候选环节；“未判断”不是硬门槛。
3. 优先提示候选环节中需要且缺失的建议文档；有文档时提示阅读环节检查要点或自行标记状态。
4. “已完成”“暂缓”以及“不需要 / 稍后”的文档不持续作为首要催促项。
5. 并行、回路或自定义图产生多个候选时，按用户的节点顺序稳定排序；用户可以直接选其他环节。

界面注明“来自所选范式”或“依据手动状态”。建议不等于强制操作，不阻止用户跳过、回退或先做其他环节。空白画布尚无节点时，提示添加环节或选用范式。

AI 可补充内容层面的理由与动作建议，但只能引用当前图中的环节，仍受用户手动状态和文档取舍约束。失效、被关闭或调用失败时回到上述规则。

## 8. GitHub 读取和刷新

连接记录使用 GitHub 返回的稳定 repository ID 标识项目，仓库名称和 URL 作为显示信息。分支名作为状态隔离键，路径和分支参数正确编码，不通过简单切割 URL 猜测含斜杠的分支名。

读取先解析选定分支的 commit SHA，再以该 SHA 读取目录和文件，保证一次展示来自同一个版本。切换仓库或分支时取消旧请求，旧响应不得覆盖当前页面。文件读取和分支选择能力以 GitHub Contents API 为基础。([仓库内容 API](https://docs.github.com/en/rest/repos/contents))

设计者建议的首版刷新行为：

- 初次连接、切换分支和用户点击刷新时读取。
- 页面可见且已授权时，默认每 60 秒检查；未授权公开浏览时默认每 5 分钟检查。
- 页面重新获得焦点时，距离上次检查超过对应间隔才检查；隐藏页面暂停定时检查。
- 采用请求队列、缓存和条件请求；显示上次读取时间与版本，变更后刷新相关文档。
- 按 GitHub 返回的限流信息延迟请求，不盲目重试；重复权限错误或路径不存在时停止无意义轮询。
- 以上是网页打开期间的检查，不承诺常驻后台同步或即时事件推送。

GitHub 官方建议在无法使用 webhook 时减少轮询并使用条件请求；已正确授权的请求返回 `304` 时不计入主要限流额度。([API 使用建议](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api))

新建空仓库没有可读取的分支或文档时仍可选择路线、复制 prompt、保存配置；待用户在外部工具提交文档后刷新。无文档时只提示缺失，不读取代码猜测进度。分支删除或仓库失去访问权限时保留已有配置，显示原因，不自动换到其他分支。

## 9. 配置保存与跨设备同步

### 9.1 三个位置的职责

| 位置 | 内容 | 写入边界 |
| --- | --- | --- |
| 工具仓库与 Pages | 网页代码、内置范式、通用 prompt、合成演示数据 | 由工具维护者发布，不包含用户项目数据 |
| 被管理的目标仓库 | 用户已有 Markdown 文档 | 本工具只读 |
| 用户独立配置仓库 | 路线、关联、命名设置、分支状态、AI 建议及依据引用、备用快照 | 用户明确保存时写入 |

建议引导用户创建私有配置仓库，避免项目名称、路径、状态或 AI 摘要意外公开。配置仓库不需要部署网页；用户自行在 GitHub 创建，工具首次保存时创建配置文件，不额外申请创建仓库的权限。

配置不复制原文档正文；AI 摘要仍可能包含项目信息，因此按私有资料处理。默认只保存证据路径和位置引用，查看时重新读取原文。不把“公开仓库可读”当成用户私人配置应公开的理由。

### 9.2 保存与冲突

- 编辑后显示“有未同步修改”，点击“保存到 GitHub”才同步，避免每次拖拽都产生 commit。
- 读取成功、保存成功、保存失败、未同步四种状态需区分。失败时保留本次草稿。
- 离开有草稿的页面时提醒；浏览器关闭后的恢复能力不应被当作远程同步成功。
- 保存使用上次读取的配置文件 SHA，顺序写入。远端已变化时停止，提供重新加载或保留本地草稿的选择，不覆盖较新的远端内容。
- 网络超时导致写入结果不确定时先重新读取核对；不得直接重试创建重复提交。
- 另一设备重新输入令牌、选择同一个配置仓库并加载后，恢复上次成功同步的配置。令牌和模型密钥不跨设备同步。

更新文件时 GitHub 提供内容 SHA 和冲突状态码，可用于检测配置并发修改。([创建或更新仓库文件](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents))

### 9.3 建议数据结构

在配置仓库的 `projects/<repository-id>.json` 中保存一个项目的完整配置，让一次保存对应一个文件更新：

- `schemaVersion`：配置格式版本；不识别的新版本只读并提示，不擅自改写。
- `repository`：稳定 ID、owner、name；不含凭据。
- `template`：采用的范式 ID、版本和副本。
- `documentRules`：允许目录、预期路径、节点关联。
- `graph`：稳定节点 ID、说明、位置、节点顺序和连线。
- `branches[branchName]`：手动状态、文档取舍、AI 建议和分析输入指纹。
- `backups`：切换范式前保留的流程及其状态快照。

用户更换分支时不继承其他分支的手动状态或 AI 结果。新分支显示“未判断”，按它自己的文档给出建议。变更共享流程时，节点 ID 稳定；删除节点涉及的旧分支状态保留在备用快照中，不错误映射到新节点。

首版一次只打开和处理一个项目；配置仓库按 repository ID 区分文件，是为了避免覆盖，不代表提供多项目总览。

## 10. 令牌与内容边界

设计者建议将两种授权分开：

1. **目标仓库读取令牌**：fine-grained PAT，仅选择需要读取的仓库，`Contents: read`。
2. **配置仓库写入令牌**：另一份 fine-grained PAT，只选择独立配置仓库，`Contents: read/write`。

同一个 fine-grained PAT 的仓库权限设置会作用于它所选的仓库；不要为了配置同步而给目标仓库一并授予写权限。不同资源所有者、组织策略可能需要不同读取令牌，首版按当前目标仓库提供相应令牌，不建设复杂账号管理器。([个人访问令牌说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens))

令牌和模型密钥默认只驻留当前页面内存；页面重新加载或换设备时需要重新输入。浏览器可以记住非秘密的配置仓库地址和显示偏好，但不自动持久化秘密。私有文档正文只在当前页面缓存；断开连接时清理相关内存数据。

GitHub 凭据只发往明确的 GitHub API；模型密钥只发往用户配置的模型端点。任何凭据不进入 URL、日志、AI 上下文、导出或 Git 配置文件。前端也不嵌入维护者的通用令牌。

Markdown 原文和模型输出都是不可信内容：安全渲染，不执行内嵌 HTML / script，不允许 `javascript:` 链接；模型没有工具调用或文件写入能力。私有资源请求不向第三方图片代理转发。错误信息避免回显请求授权头或密钥。

## 11. AI 内容分析

### 11.1 能力和触发

AI 只分析已读取的开发文档，给出内容摘要、阶段状态建议、信息不足之处和下一步理由。它不生成项目文档、不修改流程、不执行项目操作。

用户主动点击“分析当前环节”或“分析当前流程”。调用前说明要发送的文档范围和端点；批量分析一次确认范围即可，不逐份打断。普通刷新、复制 prompt、切换模式或打开网页均不自动分析。

对超出上下文预算的文档明确说明范围和未分析部分，允许缩小范围；不静默截断后声称完整分析。取消、超时、额度不足、模型不存在或格式不正确时保留原状态，不自动付费重试或切换到另一个在线服务。

### 11.2 浏览器直连的实际边界

| 方式 | 首版设计 | 已验证与待验证 |
| --- | --- | --- |
| 关闭 AI | 范式指导和手动状态照常使用 | 已确认产品需求 |
| 在线模型 | 用户提供 HTTPS 端点、模型名、个人 API key；首个接入以浏览器可访问的兼容接口为参照 | OpenRouter 预检允许所需跨域请求；尚未进行真实推理和付费调用 |
| 本地模型 | 以 Ollama 的本机接口作为首个适配参考；用户自行运行服务并允许网页来源 | 官方文档支持配置允许来源；实际浏览器、操作系统和本地模型联调待实现阶段验证 |

端点格式兼容不代表浏览器可访问。在线端点必须允许对应网页来源及授权请求头；本地服务也需要正确的 CORS 设置，并可能触发浏览器的本地网络权限。连接失败时显示针对性的排查信息，不要求关闭浏览器安全机制，不自动使用代理，不将本地分析静默改为在线分析。([Ollama 来源设置](https://docs.ollama.com/faq#how-can-i-allow-additional-web-origins-to-access-ollama)、[Chrome 本地网络访问说明](https://developer.chrome.com/blog/local-network-access))

“本地”指正在打开网页的设备，不是 GitHub Pages 服务器或 Codex 云端机器。用户在另一台设备上使用时，要在那台设备提供可访问的模型服务，或改用自行选择的在线端点。

首版承诺在线与本地连接方式可选择，不承诺所有供应商或所有浏览器都直接兼容。实现计划必须包含真实浏览器的兼容性验证，再列出已支持组合。框架或接口名不应取代这项验证。

### 11.3 输出与可追溯性

模型输出需按结构校验，至少包含当前节点 ID、建议状态或信息不足、简短理由、证据路径及对应段落位置。引用必须属于本次输入，位置可核对；无效引用不作为状态依据，明确降级为信息不足。

分析记录包含 branch、commit SHA、输入文件 blob SHA、模型标识、分析时间和范式版本。AI 判断及下一步建议均展示“根据文档判断”；主状态的选择继续遵守手动优先规则。

分析期间切换分支、修改手动状态或更新文档，完成结果也只能归入原始分支和输入版本；不覆盖当前选择或最新用户标记。

## 12. 构建者可以决定的实现细节

以下是设计者建议或留给实现计划的常规技术选择，不应继续作为用户偏好反复提问：

- 建议使用 TypeScript 和成熟组件式前端框架；画布复用成熟节点图组件，不从零实现拖拽引擎。具体框架、包管理器和依赖版本由构建者在计划中选择并记录。
- GitHub API、文档检查、范式、推荐规则、配置同步和模型调用分别形成清晰模块，避免 UI 直接混合所有网络请求。
- 路由和静态资源必须兼容 GitHub Pages 的仓库子路径；由构建者选择合适的静态路由方式。
- 配置用稳定节点 ID 和版本化格式；缓存、撤销操作、备份数量及大文件上限由构建者给出合理默认值和明确提示。
- 桌面 Safari 与 Chromium 浏览器是需要验证的目标；本地模型可按已测试组合声明支持，连接不可用时核心功能不受影响。
- 图形交互也提供可发现的按钮操作和键盘焦点，不能把所有操作隐藏在拖拽手势中。

## 13. 验收场景

| 场景 | 应观察到的行为 |
| --- | --- |
| 公开仓库、未配置 AI | 可以选择路线、读取指定文档、阅读指导并复制通用 prompt |
| 私有仓库、有适当读取授权 | 可读取文档；目标仓库没有新增文件或提交 |
| 没有文档或选定目录不存在 | 显示路线及缺失提示，允许补充、忽略或调整目录；不扫描代码 |
| 文件符合命名规范但为空 | 已找到文件，同时提示内容为空；环节不因此自动完成 |
| 文件命名不规范或多个匹配 | 可以看到文件并手动关联，不自动重命名或猜选 |
| 手动完成、AI 判断进行中 | 主状态保持手动完成，可查看 AI 理由 |
| 文档在 GitHub 上发生变化 | 下次检查刷新；旧 AI 结果标为过期，不自动调用模型 |
| 切换到另一个分支 | 图结构保持；状态、文档取舍及 AI 记录来自当前分支 |
| 未曾打开的新分支 | 不继承其他分支状态，显示未判断并读取该分支文档 |
| 标记“不需要 / 稍后再说” | 不被同一缺失文档持续占据首要建议；可以恢复 |
| 文件移动或删除 | 保留关联并提示不可用，可重新关联，恢复路径后重新读取 |
| 切换范式后想恢复 | 可恢复原流程、关联和切换时保留的状态快照 |
| 自定义并行或回路 | 画布可表达，推荐不会死循环或强制阻止跳步 |
| 在设备 A 保存，设备 B 加载 | 重新授权并连接同一配置仓库后，读取已保存的配置 |
| 两个设备同时修改 | 后保存者看到冲突并保留草稿，不静默覆盖远端 |
| 配置保存失败 | 明确显示未同步，不声称跨设备已保存 |
| 模型服务不允许跨域或本地权限未开启 | 给出可操作的连接说明，基础功能和手动状态可继续使用 |
| 复制 prompt | 剪贴板中只有通用范式，不包含项目文档或秘密 |
| 恶意 Markdown 或 AI 输出 | 不能执行脚本、发起工具调用或泄露令牌 |
| Pages 构建产物检查 | 不含用户的私有文档、凭据或配置仓库数据 |

这些是未来实现的验证要求，并非当前已经通过的产品测试。
