# 开发路线 · Development Dashboard

以 **DevFlow V3 标准八阶段**组织 GitHub 项目中的 Markdown 开发文档，让开发者和 AI 都有固定的阶段含义、明确的下一步与可追溯的状态。目标项目始终只读；工具不会生成或修改项目文档。

## 可以做什么

- 连接 GitHub 仓库，选择分支，阅读指定目录下的 Markdown；默认目录为 `docs/development`，可以在页面中调整。
- 将**固定八阶段、GitHub Markdown 文件夹树、独立文档阅读器**组成同一个工作台：点选阶段会高亮并展开关联文件，点选文档会展示完整仓库路径、关联阶段及 Markdown 正文。
- 可按路径搜索文档、查看未关联文件，并在阶段详情中绑定已有 Markdown。手机端可在「开发阶段 / 文件目录」之间切换。
- 新项目默认使用固定八阶段 V3，阶段顺序不可在网页里随意拖拽、增删或修改连线；手机上直接点选阶段卡片。
- 旧的自定义路线不会自动被覆盖；连接后可以手动迁移到标准八阶段，原有路线与分支状态会先备份。旧的自由编辑组件已移除，但仍可在历史备份中恢复以前保存的路线。
- 保留阶段内的状态、关联文档取舍与 Prompt，允许为当前分支将不适用的阶段标记为「跳过」。
- 手动标记环节状态、设置文档是否需要、查看下一步建议；状态按分支保存，手动标记优先于文档分析。
- 对缺失的文档复制通用 prompt，到自己选择的工具中使用。网页本身不生成文档。
- 可选地连接在线 OpenAI 兼容模型或本机 Ollama：先预览文档范围，再手动确认分析；结果提供证据位置及过期提示。
- 将路线、关联、状态和分析摘要显式保存到一个**独立的** GitHub 配置仓库，在另一设备重新授权后加载。

当前一次打开一个项目，仅支持 GitHub 仓库。网页不需要后端；刷新和分析仅在网页打开期间进行。

## 快速开始

需要 Node.js 24 和 npm：

```bash
npm ci
npm run dev
```

打开终端输出的本地地址。输入 `owner/repository` 或 GitHub 仓库地址，连接后可切换分支、点选八阶段、浏览文档目录和阅读正文。新仓库没有提交时仍可查看阶段指南和复制 prompt；之后点击“刷新文档”可发现新分支。

V3 标准流程默认查找以下文件，均位于 `docs/development/`。文件缺失只提示补充，不等于开发未完成；可以在阶段详情中标记文档是否需要。

```text
01-idea.md                Idea → Brainstorm
02-domain.md              Strategic DDD
03-concept-validation.md  Concept Prototype → Validation
04-roadmap.md             Roadmap
05-ui-prototype.md        UI Prototype
06-spec-plan.md           Spec → Architecture / ADR → Plan
07-implementation.md      Harness + Agent Loop
08-release.md             Human Acceptance → Release
```

文件目录树根据当前分支扫描到的 Markdown 路径生成，不改变 GitHub 文件结构。**默认只读取你配置的文档根目录**，不是整个 GitHub 仓库；只显示已扫描到 Markdown 文件的文件夹，空目录与非 Markdown 文件暂不显示。按文件名的自动匹配有多个候选时，会标为「待确认」，避免误认为已经关联。文档仍然是只读的。

`.devflow/workflow.json` 定义拟议的机器可读规范，`.devflow/state.json` 用来示范功能级状态结构。**目前 Dashboard 尚未自动从目标仓库读取这两份 JSON 作为执行状态**，实际网页状态仍按分支记录在独立的配置仓库。阶段「跳过」是人工标注，不表示完成验证或获得人工批准。

## 仓库权限与跨设备同步

公开的目标仓库可不提供令牌。私有目标仓库需要一个只选择目标仓库、具有 **Contents: read** 的 fine-grained personal access token；页面只读取该仓库，不向它写入。

如需跨设备同步，请先自行创建另一个 GitHub 仓库，建议设为私有，再提供只选择该配置仓库、具有 **Contents: read and write** 的独立令牌。在“配置同步”中连接配置仓库；修改后点击“保存到 GitHub”才会更新 `projects/<目标仓库 ID>.json`。另一设备重新输入令牌并连接相同配置仓库即可加载。

配置不主动保存读取到的文档正文或令牌，但包含仓库名称、路径、状态和可选的模型分析摘要。**模型可能在摘要中复述文档原文或敏感信息**；请在保存前检查，避免使用公开配置仓库。检测到较长的原文摘录时工具会隐藏该摘要，但无法保证识别所有复述。远端配置已变化或保存结果不确定时，工具会停止覆盖并保留当前草稿；请重新读取、核对后再操作。

令牌只保存在当前页面内存中，不跨设备同步；刷新或关闭页面后需重新输入。未同步的草稿也仅存在当前页面，离开前请先保存。

## 可选文档分析

默认关闭。在“文档分析设置”中选择在线模型或本地 Ollama，填写端点和模型名称，并按需要输入模型密钥。在线端点必须为完整的 HTTPS chat-completions URL；本地 Ollama 默认使用 `http://127.0.0.1:11434/api/chat`，它指的是**打开网页的这台电脑**，不是 GitHub 云端。

用户点击分析后，页面会列出要发送的文档和端点；确认前不会调用模型。可取消勾选文档以缩小范围，部分分析只作参考，不自动决定环节状态。字符上限是粗略上限，并不等于模型 token 数。浏览器需要得到模型服务的跨域许可，本地服务还可能受浏览器本地网络权限限制；连接失败时可继续使用无 AI 功能。实际提供商是否兼容、是否收费，以其服务设置为准。

模型只根据提供的文档给出参考，不验证代码实际运行情况；证据不合法或内容不足时不会判定完成。手动标记不会被模型覆盖。

## GitHub Pages

这个仓库包含手动触发的 `发布 GitHub Pages` 工作流。将源码推送到自己的 GitHub 仓库后，在仓库的 **Settings → Pages** 将构建来源设为 **GitHub Actions**，再到 **Actions** 手动运行该工作流。是否可对私有仓库启用 Pages 取决于 GitHub 账户和组织设置；不要为此暴露私有仓库或文档。

工作流只构建仓库里的静态网页，不读取目标项目文档，也不需要目标仓库或配置仓库的个人令牌。构建产物使用相对资源路径，支持仓库子路径部署。

## 开发检查

```bash
npm run typecheck
npm test
npm run build
npm run check:dist
npx playwright install chromium webkit
npm run test:e2e
```

`check:dist` 只检查构建目录中的合成测试隐私标记和源码映射，不是通用的秘密扫描器。浏览器测试使用合成 GitHub 和模型响应；真实服务、私有权限和浏览器环境的实际验证范围见 [验证记录](docs/verification.md)。
